URL에는 선택한 값이 있는데 화면에는 아직 반영되지 않은 상황을 생각해보겠습니다. 이런 구간을 처리하려고 복원 중이라는 플래그를 추가할 수 있습니다.

플래그 자체가 잘못된 것은 아닙니다. 비동기 작업에서는 실제로 기다리는 상태가 필요합니다. 다만 같은 선택값을 여러 곳에 저장한 뒤 서로 복사하느라 생긴 간극이라면, 플래그를 더하기 전에 각 값의 역할을 확인하는 편이 좋습니다.

이 글에서는 별도로 구성한 파일 탐색기 예제로 그 문제를 살펴봅니다. 특정 서비스의 화면이나 코드를 옮기지 않고, 선택·복원·비동기 완료라는 조건만 사용했습니다.

## 1. 같은 선택을 여러 화면에서 보여주는 경우

파일 탐색기에 폴더 트리, 경로 표시, 폴더 내용 목록이 있다고 가정하겠습니다. 선택한 폴더는 새로고침 후에도 유지되고 링크로 공유할 수 있어야 합니다.

이때 폴더 ID를 URL에 저장하는 것은 자연스럽습니다. 그런데 각 컴포넌트도 같은 ID와 선택 객체를 따로 저장하면, 어느 값이 기준인지 모호해질 수 있습니다.

```text
URL의 folder ID
       ↕
선택 스토어의 folder ID
       ↕
목록 컴포넌트의 선택 객체
```

특히 URL을 읽어 상태에 쓰는 이펙트와 상태를 읽어 URL에 쓰는 이펙트가 함께 있다면, 초기 복원 중에도 각자가 상대를 갱신할 수 있습니다.

일시적으로 값이 다른 것이 항상 버그는 아닙니다. 문제는 그 차이가 의도된 진행 상태인지, 중복 저장한 선택값이 어긋난 것인지 구분하기 어렵다는 점입니다.

## 2. URL을 기준으로 삼아도 됩니다

정렬 순서, 검색 조건, 페이지 번호처럼 URL로 충분히 표현되는 값은 URL을 읽어 화면을 파생시키는 방법이 단순합니다. 같은 값을 별도 state에 복사하지 않으면 맞춰야 할 값도 줄어듭니다. [React Router의 URL 상태 설명](https://reactrouter.com/explanation/state-management)

로딩 상태나 펼쳐진 메뉴처럼 URL에 넣지 않는 값이 있다고 해서 URL을 선택의 기준으로 쓸 수 없게 되는 것은 아닙니다. **공유할 선택값은 URL에서 읽고, 일시적인 UI 상태는 별도로 관리하는 구조도 가능합니다.**

반대로 외부 위젯의 명령형 API, 비동기 전환, 여러 입력의 처리 규칙을 하나로 묶어야 한다면 스토어에서 선택을 관리하고 URL을 직렬화하는 구조가 편할 수 있습니다.

이 글의 예제에서는 후자를 사용합니다. URL보다 스토어가 항상 우월해서가 아니라, 선택 요청과 비동기 완료를 명시적으로 구분하기 위해서입니다.

## 3. 목표와 완료 결과를 구분합니다

폴더를 선택하는 순간과 폴더 목록의 로드가 끝나는 순간은 다릅니다. 둘을 하나의 선택값으로 덮어쓰기보다 요청한 목표와 실제 완료 결과를 나눠 생각할 수 있습니다.

```ts
type FolderState = {
  targetId: string | null;
  loadedId: string | null;
  revision: number;
  status: 'idle' | 'loading' | 'ready' | 'failed';
};

type FolderAction =
  | { type: 'SELECT'; id: string | null }
  | { type: 'RESTORE'; id: string | null }
  | { type: 'LOADED'; id: string; revision: number }
  | { type: 'FAILED'; revision: number };
```

여기서 revision은 요청을 구분하는 번호입니다. URL로 공유할 값이 아니라, 늦게 도착한 이전 결과를 현재 요청과 구별하는 값입니다.

폴더 A를 선택한 뒤 곧바로 B를 선택하면 A의 응답이 더 늦게 올 수 있습니다. 완료 응답이 있다는 이유만으로 화면을 바꾸면 B를 선택한 뒤 A로 되돌아갈 수 있습니다.

목표와 결과가 다를 수 있다는 사실을 상태에 표현하고, 어떤 결과를 받아들일지 규칙을 둡니다.

## 4. 입력은 하나의 리듀서에서 처리합니다

아래 코드는 선택 변경과 오래된 완료 결과를 다루는 부분만 남긴 예제입니다.

```ts
function folderReducer(
  state: FolderState,
  action: FolderAction,
): FolderState {
  switch (action.type) {
    case 'SELECT':
    case 'RESTORE':
      return {
        targetId: action.id,
        loadedId: null,
        revision: state.revision + 1,
        status: action.id === null ? 'idle' : 'loading',
      };

    case 'LOADED':
      if (
        action.revision !== state.revision ||
        action.id !== state.targetId
      ) {
        return state;
      }
      return { ...state, loadedId: action.id, status: 'ready' };

    case 'FAILED':
      if (action.revision !== state.revision) return state;
      return { ...state, status: 'failed' };
  }
}
```

응답을 처리할 때는 요청을 시작한 시점의 revision을 함께 전달합니다. ID뿐 아니라 요청 번호도 비교하므로, A→B→A로 선택했을 때 첫 번째 A의 결과를 마지막 요청의 결과와 혼동하지 않습니다.

이 예제는 읽는 동안 이전 내용을 지우는 설계입니다. 이전 내용을 남기고 로딩 표시를 겹치려면, 그 데이터가 어떤 요청에 대응하는지 별도로 유지해야 합니다. 상태의 형태는 표시 정책에 따라 달라집니다.

리듀서는 URL이나 통신 API를 호출하지 않습니다. 갱신 규칙은 순수 함수로 두고, 요청과 히스토리 조작은 경계의 처리로 분리합니다.

## 5. URL과 연결할 때는 입력별 규칙이 필요합니다

스토어를 기준으로 해도 URL은 출력으로만 쓰이지 않습니다. 최초 진입과 브라우저 뒤로 가기에서는 입력이 됩니다.

예제에서는 다음처럼 역할을 나눕니다.

- 최초 진입에서는 URL을 파싱해 초기 상태를 만듭니다.
- 사용자가 폴더를 선택하면 선택을 갱신하고 URL에 히스토리를 추가합니다.
- 뒤로·앞으로 가기에서는 URL을 읽어 복원합니다. 이 복원으로 새 히스토리를 추가하지 않습니다.
- 잘못된 ID나 생략 가능한 값을 정규화할 때는 히스토리를 추가하지 않고 교체합니다.

```text
사용자 선택 → SELECT → 상태 갱신 + URL에 push
히스토리 복원 → RESTORE → 상태 갱신, URL 재push 없음
```

중요한 것은 “상태가 바뀌면 항상 URL에 쓴다”는 하나의 규칙으로 묶지 않는 것입니다. 복원 결과까지 다시 쓰면 뒤로 가기로 불필요한 히스토리를 만들 수 있습니다.

URL 갱신과 상태 갱신을 함께 다루는 경계가 필요합니다. 실제 구현은 사용하는 라우터의 API와 알림 방식에 맞춰야 합니다. 히스토리 API로 URL을 쓰는 동작과 사용자가 히스토리를 이동해 발생한 알림을 같은 것으로 취급하지 않습니다.

## 6. 남겨야 할 차이와 없앨 수 있는 중복

비동기 UI에는 요청한 목표와 실제 표시된 결과가 다른 시간이 있습니다. 이 차이를 모두 없앨 수는 없습니다.

반면 선택한 ID로 계산할 수 있는 라벨이나 선택 객체를 별도 state에 저장하면 데이터가 바뀔 때마다 동기화 경로가 늘어납니다. 필요할 때 ID와 최신 데이터로 계산할 수 있다면, 저장하지 않고 파생시키는 편이 단순합니다. [React의 상태 구조 설명](https://react.dev/learn/choosing-the-state-structure)

변경의 출처를 나타내는 정보도 일괄적으로 불필요하다고 할 수 없습니다. 히스토리 복원과 사용자 선택은 처리 규칙이 다릅니다. 그 차이를 액션으로 명시하고 갱신 규칙에 사용하는 데에는 의미가 있습니다.

피하고 싶은 것은 각 컴포넌트가 서로의 변경을 감시하고, 그때마다 다음 동기화를 막는 플래그를 세우는 구조입니다. 입력의 의미를 처음부터 구분하면 규칙을 한 곳에서 따라가기 쉽습니다.

## 7. 실제 화면에서 확인할 조건

예제를 화면에 연결한다면 일반적인 선택 조작 외에도 다음 조건을 확인합니다.

- URL로 복원한 초기값이 기본값의 쓰기 때문에 사라지지 않는가.
- 뒤로·앞으로 가기로 새 히스토리가 추가되지 않는가.
- 연속 선택에서 오래된 응답이 최신 화면을 덮어쓰지 않는가.
- 같은 ID를 다시 선택해도 이전 요청의 결과와 혼동하지 않는가.
- 존재하지 않는 ID, 빈 선택, 읽기 실패의 표시가 정의돼 있는가.
- URL 갱신이 실패했을 때 상태와의 불일치를 어떻게 처리할지 정했는가.

리듀서가 올바르게 동작해도 라우터나 외부 위젯과의 연결까지 올바르다고 보장하지는 않습니다. 마지막에는 렌더링된 결과와 히스토리 동작을 함께 확인해야 합니다.

## 마무리

복원 중이나 동기화 중이라는 플래그를 발견했다면, 지우기 전에 무엇을 기다리는지 확인합니다. 실제 비동기 완료를 기다린다면 필요한 상태입니다. 같은 선택을 여러 저장소에 복사하고 있다면 쓰기 역할을 다시 볼 수 있습니다.

URL과 스토어 중 무엇을 기준으로 삼을지는 화면의 조건에 따라 달라집니다. 선택 입력, 표시 결과, 히스토리 복원을 나누고, 어떤 변경이 어디에 쓰이는지 설명할 수 있는 구조를 만드는 것이 중요하다고 생각합니다.
