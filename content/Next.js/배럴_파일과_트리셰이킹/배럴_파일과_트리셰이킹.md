아이콘 하나를 가져왔는데 사용하지 않는 아이콘까지 번들에 남아 있다면 어디부터 확인해야 할까요? import가 배럴 파일을 거친다는 이유만으로 배럴을 없애기보다, 사용 방식과 모듈 실행 비용을 나눠 보는 편이 원인을 좁히기 좋습니다.

이 글에서는 별도로 구성한 작은 아이콘 예제로 재수출, 함수 호출, 동적 접근을 살펴봅니다. 특정 프로젝트의 측정 결과를 옮긴 글은 아니며, 예제의 번들 크기나 번들러별 비교 결과를 주장하지 않습니다.

## 1. 배럴은 진입점을 모으지만 제거 여부를 보장하지는 않습니다

배럴 파일은 여러 모듈을 한 곳에서 내보내는 진입점입니다.

```ts
// icons/index.ts — 설명용 예제
export { SearchIcon } from './search';
export { CloseIcon } from './close';

// 소비처
import { SearchIcon } from './icons';
```

소비처가 어떤 export를 사용하는지 정적으로 드러납니다. 번들러는 이런 정보와 부수 효과 분석을 바탕으로 사용하지 않는 코드를 제거할 수 있습니다.

다만 named import라고 항상 나머지 모듈이 사라지는 것은 아닙니다. 모듈을 읽을 때 실행해야 하는 코드가 있다면 export를 사용하지 않아도 실행 의미를 보존해야 합니다. 트리셰이킹과 모듈의 부수 효과는 함께 확인해야 합니다. [webpack의 트리셰이킹 설명](https://webpack.js.org/guides/tree-shaking/)

따라서 첫 질문은 “배럴이 있는가”보다 “배럴을 통해 무엇이 연결되고, 모듈을 평가할 때 무엇이 실행되는가”에 가깝습니다.

## 2. 재수출 형태와 소비 방식을 따로 비교합니다

다음 두 방식은 사용감이 비슷하지만 모듈 그래프에서의 형태는 다릅니다.

```ts
// 방식 A: 개별 export
export { SearchIcon } from './search';
export { CloseIcon } from './close';

// 방식 B: 네임스페이스 재수출
export * as Icons from './icons';
```

소비처에서는 각각 개별 이름 또는 객체의 속성으로 접근합니다.

```tsx
import { SearchIcon } from './ui';
<SearchIcon />;

// 다른 구성에서의 소비 예시
import { Icons } from './ui';
<Icons.SearchIcon />;
```

네임스페이스의 특정 속성만 정적으로 사용하면 번들러가 사용 범위를 분석할 수도 있습니다. 반대로 객체 전체를 다른 함수에 넘기거나 런타임 키로 접근하면 사용 범위를 좁히기 어려워질 수 있습니다.

그래서 네임스페이스 재수출 자체를 “트리셰이킹이 불가능한 문법”으로 단정하지 않습니다. 사용하는 번들러와 버전, 변환된 모듈 형태, 소비 코드에 따라 실제 결과를 비교해야 합니다.

작게 재현한다면 아래 형태를 한 번에 하나씩 바꿔볼 수 있습니다.

- 배럴에서 named export를 받고 이름으로 사용하기.
- 배럴의 네임스페이스 export에서 고정 속성으로 사용하기.
- 아이콘 서브패스를 직접 네임스페이스 import하기.
- 네임스페이스 전체를 전달하거나 동적 키로 읽기.

서브패스를 제공하는 목적도 모든 호출부가 내부 파일을 직접 읽게 만드는 데 있지 않습니다. 패키지가 지원하는 공개 진입점 안에서 사용 범위를 더 분명하게 만들 수 있습니다.

## 3. 최상위 함수 호출은 별도의 문제입니다

아이콘에 공통 속성을 붙이는 함수를 생각해보겠습니다.

```ts
export const SearchIcon = createIcon(SearchShape);
export const CloseIcon = createIcon(CloseShape);
```

이 함수가 새 컴포넌트를 반환하기만 하는지, 등록 작업이나 전역 상태 변경까지 하는지는 호출부만 보고 확신하기 어렵습니다. 따라서 결과값을 사용하지 않아도 함수 실행은 남을 수 있습니다.

함수 호출에 부수 효과가 없음을 확인했다면, 사용하는 도구가 지원하는 순수 호출 주석을 붙일 수 있습니다.

```ts
export const CloseIcon = /*#__PURE__*/ createIcon(CloseShape);
```

이는 함수를 실제로 순수하게 만들어주는 주석이 아닙니다. 도구가 호출 결과를 사용하지 않을 때 제거해도 된다는 정보를 주는 것입니다. 인자 평가에서 발생하는 부수 효과는 별도로 남을 수 있습니다. [esbuild의 순수 호출 설명](https://esbuild.github.io/api/#pure)

함수가 등록 작업을 수행한다면 이런 표시를 붙이면 안 됩니다. 번들 크기보다 실행 의미를 보존하는 것이 먼저입니다.

## 4. sideEffects 설정은 PURE 주석과 같은 역할이 아닙니다

패키지의 `sideEffects`는 사용하지 않는 모듈의 평가를 생략해도 되는지 판단하는 데 쓰입니다. 특정 함수 호출에 붙이는 순수성 표시와는 범위가 다릅니다.

모든 파일에 대해 `false`를 선언하기 전에 CSS import, 폴리필, 등록 코드처럼 모듈 평가 자체가 필요한 파일이 있는지 확인해야 합니다. 필요한 파일은 예외로 남길 수 있습니다.

```json
{
  "sideEffects": ["**/*.css", "./register.js"]
}
```

어떤 설정이 맞는지는 패키지의 실제 동작에 따라 달라집니다. “트리셰이킹을 위해 일단 false로 설정한다”는 접근은 스타일이나 초기화 코드를 함께 제거할 수 있습니다. [webpack의 sideEffects 주의점](https://webpack.js.org/guides/tree-shaking/#common-pitfalls-with-side-effects)

## 5. 동적 키가 필요하면 후보 집합을 줄입니다

문자열로 아이콘을 선택하는 API는 편리합니다. 하지만 전체 아이콘을 담은 객체에서 런타임 키로 읽으면, 어떤 항목이 필요한지 빌드 시점에 좁히기 어렵습니다.

동적 API가 필요하다면 그 API에서 사용할 후보를 명시적으로 모으는 방법이 있습니다.

```tsx
import { SearchIcon } from './icons/search';
import { CloseIcon } from './icons/close';

const iconMap = {
  search: SearchIcon,
  close: CloseIcon,
} as const;

type IconName = keyof typeof iconMap;

function NamedIcon({ name }: { name: IconName }) {
  const Icon = iconMap[name];
  return <Icon />;
}
```

여전히 동적 접근이지만 후보는 두 개로 제한됩니다. 이 두 아이콘을 모두 포함하는 비용은 받아들이고, 다른 아이콘을 후보로 연결하지 않는 방식입니다.

타입만 좁힌다고 런타임의 큰 객체에서 나머지가 자동으로 제거되는 것은 아닙니다. **후보를 담는 실제 객체도 작게 구성해야 합니다.**

대신 아이콘을 추가할 때 매핑도 갱신해야 한다는 유지 비용이 생깁니다. 어디서든 모든 아이콘을 고르게 하는 API와, 필요한 후보만 등록하는 API 중 어느 쪽이 요구사항에 맞는지 선택해야 합니다.

## 6. 지연 로딩에서는 실제 로드 경로를 확인합니다

트리셰이킹과 코드 분할은 구분해서 봐야 합니다. 하나는 사용하지 않는 코드를 제거하는 문제이고, 다른 하나는 필요한 코드를 언제 가져올지 나누는 문제입니다.

무거운 기능을 동적 import로 연결했어도, 다른 진입점에서 같은 구현을 정적으로 import하고 있다면 초기 로드에 포함될 수 있습니다. 배럴의 존재만으로 코드 분할이 무효가 된다고 단정할 수는 없지만, 정적 소비 경로가 있는지는 확인할 필요가 있습니다.

또 청크 파일이 분리됐다는 사실만으로 사용자 동작 전에는 로드되지 않는다고 판단할 수 없습니다. preload나 prefetch가 있으면 네트워크 요청은 먼저 발생할 수 있습니다.

확인할 것은 파일 이름보다 실제 사용 조건입니다. 기능을 열기 전 어떤 청크가 내려오고, 어떤 초기화가 실행되는지 봐야 합니다.

## 7. 비교는 같은 조건에서, 원인은 한 번에 하나씩

측정할 때는 개발 서버 대신 프로덕션 빌드를 기준으로 하고, 번들러·버전·옵션·진입점을 고정합니다. import 형태와 순수 호출 표시를 동시에 바꾸면 어느 변경이 영향을 줬는지 구분하기 어렵습니다.

사용하지 않는 예제 모듈에 식별 가능한 내용을 넣고 번들 분석 결과와 출력물을 함께 확인할 수 있습니다. 다만 최적화 과정에서 코드와 SVG가 변형되므로, 원본 문자열이 안 보인다는 이유만으로 제거됐다고 판단하지는 않습니다.

크기를 보고한다면 초기 청크와 비동기 청크의 범위, 압축 전과 gzip의 기준도 구분해야 합니다. 빌드 시간은 캐시와 실행 환경에 영향을 받으므로 단일 실행으로 일반화하지 않습니다.

## 마무리

사용하지 않는 코드가 남았을 때는 공개 API의 형태, 모듈 평가에 필요한 실행, 런타임 접근 범위를 나눠보면 좋습니다. 배럴 하나를 없애는 것보다 어떤 연결 때문에 코드를 유지해야 하는지 확인하는 과정이 더 중요합니다.

순수성 주석과 패키지 설정은 분석을 돕는 정보입니다. 실제 부수 효과를 없애거나 잘못된 구조를 대신 고쳐주지는 않습니다. 작은 예제로 원인을 분리하고, 마지막에는 실제 프로덕션 결과에서 제거와 로드 여부를 확인해야 합니다.
